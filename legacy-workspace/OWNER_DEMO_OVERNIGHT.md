# Verdigris Owner Demo — overnight orchestration brief

## Objective

Produce one integrated native C++ Owner Demo that convinces the sole developer
the conversion can become Verdigris. The build must improve the recognizable
player journey, not merely add passing internal contracts.

## Success rule

A task is complete only when it does at least one of the following:

1. Improves the integrated playable Owner journey.
2. Produces visible or measured acceptance evidence.
3. Unlocks a named, automatically released successor.

Tests are necessary but do not prove visual fidelity, combat feel, menus,
inventory usability, instance navigation, or WIZARD integration.

## Hard requirements

- Branded splash and menus; Escape never quits directly.
- Animated player and enemies with visible weapons and attacks.
- Attack arcs, trails, projectiles, hits, telegraphs, reactions, and deaths.
- No primitive circle or rectangle stand-ins in normal play.
- Raster WIZARD Framekit panes and faithful resource orbs.
- Grid backpack, paper doll, tooltips, equipment interaction, and real item art.
- Chronicles faction, House, Scion, occupation, mortality, and recovery seams.
- Village-defense prologue and persistent non-combat town.
- Multiple generated combat zones with readable physical gates.
- Persistent instances and control-click fresh-instance requests.
- First level opens the geometric tree.
- One bounded spell-lattice transformation.
- Trophies, reagents, Brands, slow Bond progress, and one local recovery proof.
- First Scion-versus-House investment and visible House development fork.
- One-command owner launcher and morning evidence package.

## Explicit exclusions

- Six auxiliary inventory windows in the opening; they belong around levels
  20–40.
- Full global item circulation and Legends scaling.
- Complete campaign, endgame, seasons, companions, or production economy.
- Final mortality-mode balance.
- Final production art for every actor, item, biome, and effect.
- Public launch or large-server readiness.

## Repository safety

The primary Verdigris checkout contains user and worker state and is not a safe
implementation workspace. Do not switch branches, reset, clean, or repurpose
it. Every implementation lane uses an isolated clean worktree based on the
authoritative program branch.

Assign exactly one owner each for the client integration hotspot, core
simulation, and networking. Other workers expose new modules and fixtures for
the integrator rather than editing those shared files concurrently.

## Lane A — integration and renderer

1. Establish clean integration and worker worktrees.
2. Select and land the native GPU presentation foundation, or a tightly bounded
   bridge that does not become permanent architecture.
3. Extract actor, world, HUD, pane, and overlay draw APIs from the client
   hotspot.
4. Define texture-atlas, animation, nine-slice, and shader interfaces.
5. Integrate worker modules sequentially.
6. Publish a playable owner build after each green merge.
7. Record frame time, memory, startup time, and draw workload.

## Lane B — actors, combat presentation, and audio

1. Animate vector or articulated player and enemy actors.
2. Attach visible direction-aware weapons and poses.
3. Implement swings, thrusts, slams, casts, projectiles, and movement skills.
4. Implement arcs, trails, hit reactions, death animation, and loot transitions.
5. Make telegraphs readable and answerable.
6. Connect the existing audio scheduler to an audible backend.
7. Author movement, attack, impact, damage, death, pickup, level-up, and UI cues.
8. Add scenarios that reject invisible attacks and static actor regressions.

## Lane C — WIZARD Framekit, menus, orbs, and inventory

1. Correct the WIZARD Framekit wave: slice the generated artwork rather than
   inventing generic CSS substitutes.
2. Produce transparent atlases and metadata for corners, borders, dividers,
   panel fills, slots, circular frames, buttons, tabs, and ornaments.
3. Define nine-slice margins, anchors, safe stretch regions, and DPI behavior.
4. Reconstruct the reference wireframe and require side-by-side visual review.
5. Implement native main, pause, settings, House, character, inventory, and exit
   menus using the raster kit.
6. Make Escape close the top pane or open pause; exit only through menu or
   window close.
7. Port faithful WIZARD resource-orb presentation.
8. Implement grid backpack, paper doll, equipment seats, tooltips, and item
   movement.
9. Load actual WIZARD RPG Inventory art.
10. Display Brands, Bond progress, trophies, reagents, coins, and provenance.
11. Apply the corrected kit to WIZARD Inventory, Skill Tree, HUD, and other
    modules as compatibility pressure tests.

## Lane D — town, content generation, and instances

1. Build the village-defense prologue.
2. Build the persistent non-combat town.
3. Add elder/steward, weapons-and-tools trainer, and armor/ritual merchant.
4. Wire shop, storage, House investment, guidance, and expedition access.
5. Port or adapt Cartographer output into deterministic native content.
6. Produce at least three visually and structurally distinct combat layouts.
7. Guarantee entrance, main route, optional branch, objective, boss, exit, and
   connectivity.
8. Add physical gate landmarks with hover highlight and destination label.
9. Persist instance state for a defined lifetime.
10. Normal gate use re-enters; control-click explicitly creates a fresh
    instance.
11. Add negative tests for disconnected maps, missing exits, and accidental
    rerolls.

## Lane E — progression, Chronicles, items, and House

1. Wire faction, House name, Scion name, and prior occupation.
2. Keep the first Scion classless; occupation supplies only a starting nudge.
3. Trigger first level at the prologue boss.
4. Open the real geometric tree and persist one allocation.
5. Expose one bounded spell-lattice element or component choice.
6. Implement trophies and concrete reagents.
7. Apply one or two basic Brands.
8. Show slow Bond progression without granting a mature Bond.
9. Stage one locally recoverable historical item.
10. Implement the first-return choice: Scion equipment or durable House value.
11. Offer the initial House fork: Stores and Cultivation, Materials and
    Workshop, or Caravan and Exchange.
12. Represent daily claim, treasury upkeep, offline production, storage cap,
    and safe pause.

## Lane F — owner journey, QA, and release

1. Add scenario coverage for every new input-to-simulation-to-render path.
2. Capture normal play at multiple resolutions.
3. Compare presentation against the JavaScript game and WIZARD references.
4. Run all native build, unit, networking, session, and client-scenario gates.
5. Manually play setup, defense, boss, tree, town, investment, generated zone,
   skill transformation, loot, Brand, recovery, and return.
6. Reject primitive placeholders, invisible attacks, broken Escape behavior,
   list inventory, missing gates, or one-map regressions.
7. Package a one-command owner launcher.
8. Produce a morning handoff with exact commits, gates, captures, performance,
   known defects, and named successors.

## Always-on coordinator loop

1. Observe program tip, claims, gates, captures, defects, and owner-journey
   score.
2. Maintain a dependency graph and collision map.
3. Release only exact, path-disjoint, acceptance-ready work.
4. Integrate continuously rather than waiting for the entire wave.
5. On failure, revise, split, reassign, or compare competing prototypes.
6. Generate successor tasks before the executable runway empties.
7. Wake expensive planners for conflicts, protected surfaces, owner choices, or
   repeated unexplained failure.
8. Never mark visible product work complete based only on unit tests.

## Morning evidence

- One command launches and exits cleanly without orphan processes.
- The native gate and complete client scenario suite pass.
- A manual Owner journey is recorded.
- Captures show WIZARD UI, orbs, inventory art, animated combat, town, and
  varied zones.
- Performance measurements are recorded with the tested resolution and build.
- Every incomplete requirement has a named successor and dependency.

## Longer runway after the Owner Demo

Expand the living goal graph just in time across campaign acts, enemy and item
families, auxiliary inventory windows, mortality modes, item circulation,
companions, cooperative play, House economy, trading, persistence, performance,
packaging, seasons, endgame, and large-server scaling. Keep hundreds or
thousands of goals latent, but only a dependency-validated executable runway
active.
